# Controller

## Overview

This package implements the trajectory tracking controller layer for the autonomous driving planning stack.

It consumes the velocity-profiled trajectory generated by the velocity profiler and ego vehicle odometry from CARLA, then publishes normalized CARLA vehicle control commands.

The controller uses:

- CARLA ego vehicle odometry
- Velocity-profiled trajectory from the velocity profiler
- Pure Pursuit lateral tracking
- PID-based longitudinal speed tracking
- Kinematic bicycle (front-steer Ackermann) vehicle model
- Steering-rate limiting and command smoothing
- Stop-point enforcement from upstream trajectory metadata

Published output:

- `/carla/ego_vehicle/vehicle_control_cmd`

## Purpose

The goal of this task is to convert the planned and velocity-profiled trajectory into low-level vehicle commands.

The controller is responsible for:

- tracking the local trajectory geometry
- following the velocity profile generated by the velocity profiler
- converting steering and acceleration requests into CARLA commands
- stopping safely when trajectory or odometry data is missing or stale
- enforcing hard stop points near red lights, obstacles, or the final goal

It does not handle:

- global route generation
- behavior decision making
- obstacle avoidance planning
- velocity profile generation
- traffic light reasoning

Those responsibilities are handled by earlier planning stack modules.

## System Design

The package is divided into three main parts:

1. Pure C++ vehicle model
2. Pure C++ Pure Pursuit controller
3. ROS 2 controller node

Pipeline:

```text
Velocity-Profiled Trajectory + CARLA Odometry
        ↓
ControllerNode
        ↓
Trajectory trimming and message conversion
        ↓
PurePursuitController
        ↓
VehicleModel
        ↓
carla_msgs/CarlaEgoVehicleControl
```

## Controller Library

The controller logic is implemented as reusable C++ classes without ROS 2 dependencies where possible.

Main files:

- `include/controller/pure_pursuit_controller.hpp`
- `src/pure_pursuit_controller.cpp`
- `include/controller/vehicle_model.hpp`
- `src/vehicle_model.cpp`

Responsibilities:

- compute dynamic lookahead distance
- select a lookahead target from the local trajectory
- compute Pure Pursuit curvature
- convert curvature to front steering angle
- track target velocity using PID speed control
- clamp acceleration and steering commands to vehicle limits
- support optional coordinated rear steering
- convert physical commands to normalized CARLA actuator commands

This keeps the core tracking logic independent from ROS 2 communication.

## Controller Node

The ROS 2 node wraps the controller and vehicle model.

Main files:

- `include/controller/controller_node.hpp`
- `src/controller_node.cpp`

Responsibilities:

- subscribe to the velocity-profiled trajectory
- subscribe to ego vehicle odometry
- validate input freshness
- trim the trajectory around the ego vehicle
- convert trajectory messages to internal controller points
- run Pure Pursuit and speed control at a fixed rate
- enforce close-range stop points
- publish CARLA vehicle commands
- publish safe brake commands when input data is invalid

Subscribed topics:

- `/velocity_profiler/trajectory`
- `/carla/ego_vehicle/odometry`

Published topics:

- `/carla/ego_vehicle/vehicle_control_cmd`

## Control Approach

The controller uses Pure Pursuit for lateral trajectory tracking and PID speed control for longitudinal motion.

Control flow:

```text
Latest trajectory
   ↓
Find nearest point to ego vehicle
   ↓
Keep forward reference window
   ↓
Select lookahead target
   ↓
Compute target curvature
   ↓
Convert curvature to steering
   ↓
Read target velocity from trajectory
   ↓
Compute acceleration using speed PID
   ↓
Apply limits, filtering, and CARLA conversion
```

## Pure Pursuit lateral control

The controller selects a lookahead point along the local trajectory and transforms it into the ego vehicle frame.

The lateral offset of the lookahead point is used to compute path curvature:

```text
curvature = 2 * local_y / lookahead_distance^2
```

The curvature is then converted to a front steering command using the configured wheelbase and steering limits.

The lookahead distance is speed-dependent:

```text
lookahead = max(min_lookahead_distance,
                lookahead_distance + lookahead_time_gain * current_speed)
```

This improves stability at higher speed while preserving a minimum lookahead distance at low speed.

## Longitudinal speed control

The longitudinal controller tracks the velocity generated by the velocity profiler.

For each control step:

- the controller reads the target speed from the lookahead trajectory point
- if the lookahead point has no valid speed, it scans forward for the next valid non-zero speed
- if the trajectory represents a deliberate stop, target speed is set to zero
- a PID controller computes the desired acceleration
- acceleration is clamped to configured acceleration and deceleration limits

The PID state is reset when:

- trajectory data is stale
- odometry data is stale
- the trajectory is too short
- a hard stop is commanded
- controller output is invalid

## Vehicle Model

The vehicle model is a kinematic bicycle model with front-wheel Ackermann steering.
It also contains a counter-phase rear-steering mode (double Ackermann), but that
mode is model-only: CARLA's `CarlaEgoVehicleControl` accepts a single steering
command, so the node rejects `double_ackermann.enable_rear_steering: true` at startup.

Main responsibilities:

- clamp front and rear steering commands
- clamp acceleration commands
- apply front steering-rate limits
- coordinate rear steering when enabled
- propagate vehicle state for prediction or testing
- convert acceleration into throttle/brake commands
- convert steering angle into normalized CARLA steering command

Kinematic model equations:

```text
beta = atan2(lr * tan(delta_front) + lf * tan(delta_rear), wheelbase)
x_dot = v * cos(psi + beta)
y_dot = v * sin(psi + beta)
psi_dot = (v / wheelbase) * (tan(delta_front) - tan(delta_rear))
v_dot = acceleration
```

Rear steering is disabled by default in the YAML configuration. When enabled, the model applies counter-phase rear steering using the configured rear steering ratio.

## Stop-Point Handling

The controller respects stop metadata generated by upstream modules.

Each trajectory point may contain:

- `is_stop_point`
- `stop_reason`
- `longitudinal_velocity_mps`

The controller does not decide why the vehicle should stop. It only enforces the stop when a stop point with near-zero velocity is close enough to the ego vehicle.

If the stop point is within the hard-stop guard distance, the controller publishes:

- zero throttle
- full brake
- zero steering

This helps prevent creeping through:

- red traffic lights
- obstacle stop points
- goal stop points

## Safety and Freshness Checks

The controller only computes commands when both trajectory and odometry are available and fresh.

If data is missing or stale, the node publishes a safe brake command instead of reusing old commands.

Configured freshness limits:

- trajectory timeout
- odometry timeout

This prevents the vehicle from driving using outdated route or ego-state information.

## Command Smoothing and Limits

Before publishing to CARLA, the controller applies:

- steering-rate limiting
- steering low-pass filtering
- acceleration low-pass filtering
- front steering clamp
- rear steering clamp
- acceleration/deceleration clamp
- normalized throttle/brake/steer conversion

The final command is published as:

```text
carla_msgs/msg/CarlaEgoVehicleControl
```

## Build

From the workspace root:

```bash
colcon build --packages-up-to controller
source install/setup.bash
```

## Run

Start CARLA first:

```bash
cd ~/CARLA_0.9.16
./CarlaUE4.sh
```

Start the CARLA ROS bridge with the ego vehicle:

```bash
ros2 launch carla_ros_bridge carla_ros_bridge_with_example_ego_vehicle.launch.py
```

Launch the controller:

```bash
ros2 launch controller controller.launch.py
```

Or run it as part of the full planning stack after the velocity profiler is publishing `/velocity_profiler/trajectory`.

## Runtime Verification

Check that the controller node is running:

```bash
ros2 node list | grep controller
```

Check the subscribed trajectory topic:

```bash
ros2 topic info /velocity_profiler/trajectory -v
```

Check the subscribed odometry topic:

```bash
ros2 topic info /carla/ego_vehicle/odometry -v
```

Check the published CARLA command:

```bash
ros2 topic echo /carla/ego_vehicle/vehicle_control_cmd
```

Expected command fields:

- `throttle`
- `brake`
- `steer`
- `hand_brake`
- `reverse`
- `gear`
